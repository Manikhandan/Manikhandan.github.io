ML development lifecycle · From data through retrain — two graphs, not one script

End-to-End MLOps Pipeline

Feature engineering, evaluation gates, experiment runs, retrain trigger

The ML development path (ingest, validate, features, train, evaluate) is a different graph from the MLOps automation path (register, promote, package a serving bundle). A monitor stage can raise a retrain trigger when PSI or error rate crosses a threshold.

Capability
Full ML development path: ingest, validate, features, train, evaluate — then a separate deploy graph.
Evaluation
Holdout roc_auc and recall gates. A failed evaluate records a StageError and does not register.
Deployment
package freezes the Production alias into a serving bundle. Airflow is an optional wrapper, not a requirement.
Monitoring
A monitor stage reads observed PSI / error rate and can raise a retrain trigger.
Failures
Non-finite data, class imbalance, quality rejection, missing alias, and 503 on /score without a model.

Problem

One script that trains and copies a file into a serving folder hides the moment a model becomes the thing you actually run. Training is a batch job with gates. Deployment is a freeze of a version.

ML development vs MLOps automation

The ML path is ingest → validate → preprocess → features → train → evaluate. The ops path is register → promote, then a separate package stage. They share ArtifactStore and fail independently. Airflow is an optional wrapper around the same callables.

Data flow

Raw npz lands in var/store/runs/<id>/. Validation refuses non-finite features and extreme class imbalance. Feature enrichment (an interaction column) is a function imported by both training and serving so the contract cannot drift silently.

Quality gates

evaluate fails the run if roc_auc or recall is below settings. Nothing is registered. Promotion is a later stage, not a side effect of fit().

Retrain trigger

monitor reads observed_psi and observed_error_rate. retrain_trigger raises if PSI ≥ threshold or error rate ≥ 0.15. The pipeline does not loop forever; the trigger is a signal to run_training again.

Failure handling

Each stage records StageResult. Failures become StageError with the stage name. The serving API returns 503 if the Production alias is missing.

What I would improve next

Remote store with locking around promotion, dataset hashes on raw npz, and a canary package stage that scores a holdout before flipping Production.

Engineering decisions

Why not one DAG that trains and deploys?
Because they fail differently. A bad roc_auc should not rebuild a serving bundle. A packaging failure should not rerun ingest.
Why is Airflow optional?
The graph has to be testable with pytest. A scheduler is an adapter. dags/mlops_dag.py calls the same functions.
